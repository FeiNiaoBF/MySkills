# 代码与项目「做减法」Skill

## 核心理念

**减法不是偷懒，是主动剔除不必要的复杂度。**

三条黄金原则：
- **YAGNI**：You Aren't Gonna Need It — 未来可能用到 ≠ 现在就要写
- **DRY**：Don't Repeat Yourself — 重复出现三次以上必须抽象
- **KISS**：Keep It Simple, Stupid — 最简能跑通的实现优先

衡量标准：**新同事一个月后能否更快地理解并修改这个系统？**

## 工作流程：如何帮助用户做减法

### Step 1：分析输入，识别减法机会

收到用户的代码/项目描述后，按以下三个层次系统扫描：

| 层次 | 目标 | 典型信号 |
|------|------|----------|
| **句法层**（代码行） | 减少代码行数 | 死代码、注释块、重复片段、冗余条件 |
| **结构层**（模块连接） | 减少连接数 | 过深层级、单实现接口、只被一处调用的模块 |
| **本质层**（概念数量） | 减少概念数 | 过时功能、过度抽象、无人用的配置项 |

### Step 2：评估风险，分级处理

对每个减法候选项，判断风险等级：

```
🟢 低风险（可直接建议删除）
  - 注释掉的代码块
  - 未使用的 import / 变量 / 常量
  - 重复的工具函数（有测试覆盖）
  - 显然的冗余条件（如 if true / if false）

🟡 中等风险（建议先标记废弃，观察后再删）
  - 只有单一实现的接口
  - 调用次数极少的内部函数
  - 未使用的配置项（需确认无动态读取）
  - 注释说明"将来可能用到"的代码

🔴 高风险（必须有测试覆盖 + 充分分析后才删）
  - 对外暴露的公共 API
  - 核心路径上的防御性代码
  - 性能关键区域的"奇怪写法"（可能是微优化）
  - 没有测试的任何东西
```

### Step 3：给出具体的减法建议

对每处减法机会，输出：
1. **位置**：哪里（函数名 / 行号 / 模块名）
2. **问题**：这里为什么是"多余的复杂度"
3. **操作**：具体怎么删或怎么合并（给出改后代码）
4. **风险**：删除的风险和验证方法

### Step 4：给出安全删除的操作流程（如果用户需要）

```
1. 探测  → 静态分析 + 确认候选项真的没有执行
2. 标记  → @deprecated / // willremove:2025-Q3，通知同事
3. 观察  → 发布后观察 1~2 周，看错误日志有无异常
4. 删除  → PR 中明确说明删了什么、为什么
5. 清理  → 同步删除对应的测试、注释、文档
```

## 各场景减法速查

### 代码层面

**删除死代码**
- 注释掉的大段代码 → 直接删（有 Git 不怕找不回来）
- 未使用的 import → 工具自动检测（ESLint no-unused-vars、Pyright、go vet）
- 未使用的函数/变量 → IDE "Find Usages" 确认后删除

**合并重复逻辑**
```python
# ❌ 减法前：重复
def process_user(user): validate(user); log("user"); save(user)
def process_admin(admin): validate(admin); log("admin"); save(admin)

# ✅ 减法后：参数化
def process_entity(entity, kind): validate(entity); log(kind); save(entity)
```
⚠️ 警惕过度参数化：为消除两行重复引入几十行配置，得不偿失。

**简化条件（卫语句）**
```javascript
// ❌ 减法前：嵌套
function process(data) {
  if (data) {
    if (data.valid) {
      if (data.items.length > 0) {
        return doWork(data);
      }
    }
  }
}

// ✅ 减法后：提前返回
function process(data) {
  if (!data || !data.valid || data.items.length === 0) return;
  return doWork(data);
}
```

**减少不必要的抽象**
- 接口只有一个实现且不会扩展 → 删除接口，用具体类
- 只调用一次的函数且不表达独立概念 → 内联
- `service → manager → handler → util` 四层 → 考虑合并为两层

### 依赖层面

```bash
# 检测未使用的依赖
npm:   npx depcheck
maven: mvn dependency:analyze
go:    go mod why <package>
pip:   pip-extra-reqs / deptry
```

优先用语言内置 API 替代外部库（如 `fetch` 替代 `axios`，`java.net.http` 替代 Apache HttpClient）。

### 模块/服务层面

合并信号：
- 两个模块**频繁一起修改**且被**相同调用方**使用 → 合并
- 一个"独立服务"只被**一个调用方**使用 → 降级为内部函数
- 接口**半年内无调用** → 下线

## 什么时候不要做减法

| 情况 | 原因 | 正确做法 |
|------|------|----------|
| 核心路径且无测试 | 删错了无法验证 | 先补测试 |
| 对外公共 API | 会破坏调用方 | 走 deprecation 周期 |
| 性能关键的"奇怪写法" | 可能是微优化 | 保留注释说明原因 |
| 处理边界/异常的防御代码 | 看似多余实则防崩溃 | 先确认异常不可能发生 |

**黄金法则：在做减法前，先要有充分的测试覆盖。没有测试的删除是盲目的。**

## 输出格式要求

对用户提供的代码做减法分析时，输出结构：

```
## 减法分析报告

### 🔍 扫描结果（共发现 N 处）

| 编号 | 层次 | 位置 | 问题 | 风险 |
|------|------|------|------|------|
| 1    | 句法 | ...  | ...  | 🟢   |

### 📋 逐项建议

#### #1：[简短标题]
**问题**：...
**建议**：删除 / 合并 / 内联
**改后代码**：
```[语言]
...
```
**风险**：低 / 中 / 高，[验证方法]

### ✅ 安全删除顺序
1. 先删 🟢 低风险项（...）
2. 再处理 🟡 中等风险项（先标记废弃）
3. 🔴 高风险项建议补测试后再操作
```

如果用户只是问"怎么做减法"的概念性问题，用自然语言回答即可，不需要套用报告格式。
