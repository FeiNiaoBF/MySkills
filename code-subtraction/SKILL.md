# code-subtraction — 代码与项目「做减法」

帮助工程师安全地删除不必要的复杂度，让系统更易读、更稳定、更易修改。
详细场景手册（各层次减法速查、输出报告格式）见 [references/subtraction-playbook.md](references/subtraction-playbook.md)。

## 核心理念

**减法不是偷懒，是主动剔除不必要的复杂度。**

- **YAGNI**：未来可能用到 ≠ 现在就要写
- **DRY**：重复出现三次以上必须抽象（但警惕为消除两行重复引入几十行配置）
- **KISS**：最简能跑通的实现优先

衡量标准：**新同事一个月后能否更快地理解并修改这个系统？**

## 工作流程

### Step 1：三层次扫描，识别减法机会

| 层次 | 目标 | 典型信号 |
|------|------|----------|
| **句法层**（代码行） | 减少代码行数 | 死代码、注释块、重复片段、冗余条件 |
| **结构层**（模块连接） | 减少连接数 | 过深层级、单实现接口、只被一处调用的模块 |
| **本质层**（概念数量） | 减少概念数 | 过时功能、过度抽象、无人用的配置项 |

### Step 2：风险分级

- 🟢 **低风险**（可直接建议删除）：注释掉的代码、未使用的 import/变量、显然的冗余条件
- 🟡 **中等风险**（先标记废弃，观察后再删）：单实现接口、极少调用的内部函数、未使用的配置项
- 🔴 **高风险**（测试覆盖 + 充分分析后才删）：公共 API、核心路径防御代码、性能关键区的"奇怪写法"、无测试的任何东西

### Step 3：消融实验（Ablation Study）

**先消融，再删除。** 借鉴机器学习的 ablation study：每次只移除一个组件，对照系统行为差异，用证据决定去留。这把"我觉得它没用"变成"证明它没用"。

```
1. 基线   → 先跑现有测试 + 冒烟验证，记录行为（输出、日志、关键指标）
2. 消融   → 只移除一个候选项，不做任何其他改动（git stash 或独立分支）
3. 对照   → 重跑同样的测试与冒烟，与基线逐项对比
4. 判定：
   无差异  → 证据支持删除（仍受 Step 2 风险等级约束）
   有差异  → 该代码有真实作用，立即恢复，并在报告中记录它的实际用途
```

消融纪律：

- **单变量原则**：一次只消融一个候选项，否则无法归因
- **可回滚**：每次消融必须在独立分支或 stash 上进行，随时可恢复
- **结果入档**：把消融结论写进减法分析报告，作为删除依据
- **边界**：消融验证的是"当前是否被使用"，不能证明"未来不需要"；对 🔴 高风险项，无测试覆盖时消融仍是盲目的——先补测试

### Step 4：给出具体减法建议

每处机会输出：**位置**（函数/行号/模块）→ **问题**（为什么多余）→ **操作**（怎么删/合并，附改后代码）→ **风险与验证方法**。

### Step 5：安全删除流程（涉及线上/共享代码时）

```
探测 → 静态分析确认候选项真的无执行
标记 → @deprecated / // willremove:<日期>，通知同事
消融 → 按 Step 3 在预发/本地做一次完整消融对照
观察 → 发布后观察 1~2 周，看错误日志有无异常
删除 → PR 中明确说明删了什么、为什么、消融证据是什么
清理 → 同步删除对应的测试、注释、文档
```

## 什么时候不要做减法

| 情况 | 原因 | 正确做法 |
|------|------|----------|
| 核心路径且无测试 | 删错了无法验证 | 先补测试，再消融 |
| 对外公共 API | 会破坏调用方 | 走 deprecation 周期 |
| 性能关键的"奇怪写法" | 可能是微优化 | 消融对照性能指标后再决定 |
| 边界/异常的防御代码 | 看似多余实则防崩溃 | 先证明异常不可能发生 |

**黄金法则：没有测试覆盖的删除是盲目的；没有消融对照的删除是猜测。**
