# RESOURCES.md Format

`RESOURCES.md` is the curated source list for one technology route. Use it to ground explanations and project choices instead of relying on unverified memory.

## Template

```md
# {Technology} Resources

## Knowledge

- [{Title}](https://example.com)
  {What it covers, the version or date that matters, and when to use it.}

## Practice

- [{Repository, benchmark, or specification}](https://example.com)
  {What a learner can inspect or run, and which project capability it supports.}

## Wisdom (Communities)

- [{Community or maintainer discussion}](https://example.com)
  {Why it is high-signal and when real-world feedback from it is useful.}

## Gaps

- {A mission-critical area without a trustworthy source or practical example.}
```

## Rules

- **High-trust first.** Prefer official documentation, standards, original papers, maintainers, recognized experts, and well-moderated communities.
- **Annotate every entry.** Record what it supports, the relevant version/date, and when to reach for it.
- **Record compatibility.** Note runtime, framework, model, dataset, or API versions when changing them could invalidate a project.
- **Separate knowledge from wisdom.** A community discussion can provide practice insight without becoming the authority for an API or safety claim.
- **Surface gaps.** An explicit gap drives the next source search; it is better than a confident-looking weak link.
- **Prune.** Remove shallow, stale, wrong, or off-mission material instead of burying it in a long list.
