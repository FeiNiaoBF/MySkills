# Project Brief Format

Every micro-project, transfer check, and capstone begins with a brief at `projects/<number>-<name>/BRIEF.md`. The brief makes the learning target and definition of done visible before implementation starts.

## Template

```md
# {Project name}

## Problem
{A concrete user or system outcome.}

## Capability
{The one capability this project adds or tests.}

## Constraints
- {Scope and time boundary}
- {Tools, versions, data, or hardware boundary}
- {Design decision the learner must make}

## Starting point
{Existing code, mechanical scaffold, and what the learner owns.}

## Definition of done
- Machine: {exact command, assertion, metric, or evaluation}
- Human: {behavior, screenshot, recording, output, or error sample}
- Learner: {questions the learner must answer in the reflection}
```

## Rules

- Name one primary capability. Connected supporting concepts belong in the explanation, not as extra hidden objectives.
- State what a scaffold contains and what the learner must implement.
- Make the evidence observable and reproducible where the domain allows it.
- Keep a capstone brief goal-and-constraint driven; leave the implementation sequence open.
