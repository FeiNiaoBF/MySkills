# Frontend Guide — 模块化前端陪建

面向**不懂前端**的用户：用户负责想法和决策，agent 负责全部代码。核心方法论是把页面看作**模块的堆叠**——每个模块有明确的职责、内容和尺寸规格，逐个设计、逐个构建、逐个确认。

## 硬约束

- **技术栈固定**：单文件 HTML + CSS + JS，零工具链，浏览器直接打开即见结果。除非用户主动要求，不引入框架、构建器、npm。
- **结构必须模块化**：一个模块 = 一个带注释边界的 `<section>`（`<!-- ═══ 模块：hero ═══ -->` 风格标记开头结尾）；颜色、字体、间距定义为 `:root` CSS custom properties（design tokens）。这样未来迁框架是机械搬运，不是重设计。
- **每次只交付一个模块**，见 Step 3 的 gate。
- 教学穿插但不阻塞：每个模块交付时附一段 2-4 句的「为什么这样切/这样写」，每次构建最多讲 1-2 个概念点，多了就是噪音。

## 流程

### Step 1 — 确认大方向（direction gate）

动手写任何代码前，先和用户对齐四件事，输出一张**方向卡**：

| 项 | 要问清的 |
|---|---|
| 页面范围 | 单页还是多页？多页时先列页面清单（每页一句话职责），模块地图从用户最急的那一页开始 |
| 页面用途 | 这是什么页面？给谁看？看完希望对方做什么？ |
| 内容清单 | 页面上必须出现哪些内容（文字/图片/按钮/列表…）？让用户用大白话列 |
| 风格方向 | 想要什么感觉？（用户往往说不出术语——给 2-3 个带具体描述的选项让其挑选，而不是问「你喜欢什么风格」） |
| 硬约束 | 需要适配手机吗？有没有必须用的图片/品牌色？ |

把方向卡完整复述给用户，**用户确认后才进 Step 2**。用户意图本身还模糊时，先走 `brainstorming` skill 澄清意图，再回到这里。

完成标准：用户对方向卡说了「对/可以/就这样」。

确认后立即把视觉决定落盘到项目根目录的 `DESIGN.md`（已有则更新）：方向卡里的风格选择 → Overview/Colors/Typography 叙述，颜色/字体/间距抽成 YAML front matter tokens，附 Do's and Don'ts。书写格式走 `better-designs-md` skill。这样后续模块构建与未来会话保持同一套视觉，不靠记忆。

### Step 2 — 模块地图（module map）

按前端的结构思维，把方向卡的内容清单切成**从上到下的模块序列**（典型：header → hero → 内容区 ×N → footer）。每个模块一行规格，产出一张**模块地图表**给用户确认：

| # | 模块 | 职责（一句话） | 包含元素 | 尺寸规格 | 优先级 |
|---|---|---|---|---|---|
| 1 | header | 品牌与导航 | logo 文字、3 个导航链接 | 宽 100%，高 ~64px，吸顶 | P0 |

尺寸规格要给**具体数值**：宽度策略（100% / 限宽 1200px 居中 / 固定侧栏 260px）、高度或高宽比、移动端折叠行为（堆叠 / 横向滚动 / 隐藏）。数值先给合理默认，用户看了实际效果后再调——**规格是可修订的合同，不是一次到位的图纸**。

顺序策略：P0 模块（没有页面就不成立的）先进；让用户看到地图时能指着说「这个不要、这个放最后」。

完成标准：用户确认了模块序列和每个模块的存在与优先级。

### Step 3 — 逐模块构建（module gate）

按地图顺序，**一次只做一个模块**：

1. 定规格：把该模块的尺寸/间距/字号落成具体 CSS（引用 `:root` tokens，不写魔法数）。
2. 实现：写入 HTML 对应 `<section>` 与 CSS/JS；标记注释标明模块边界。
3. 视觉检查点：让用户**刷新浏览器亲眼看**，用大白话反馈（「太挤了」「图太小了」），agent 负责翻译成 CSS 修改。
4. 附「为什么」：讲这个模块为什么这样切分/布局（≤2 个概念点）。
5. Gate：用户说「下一个」，才进下一模块。

用户对某处不满意时**只修那一处**（重排局部、调一个数值），不重做整个模块——重做会丢掉已确认的工作，还引入新问题。

用户反馈要求改地图本身（加/删/换模块顺序）时，回到 Step 2 更新地图再继续——改在代码前便宜，改在代码后贵。

完成标准：每个模块都经过了视觉检查点并被用户放行。

### Step 4 — 整页完善（polish pass）

所有模块就位后，做一轮全局整理，逐项过：

- **响应式**：手机宽度下逐模块检查（缩窗或 devtools 设备模拟），修折叠行为。
- **节奏一致**：模块间距、标题层级、留白是否统一（应该都来自 tokens，不一致 = 有魔法数漏网）。
- **可访问性底线**：图片有 alt、文字对比度够、可点元素够大。
- **空态与极端内容**：标题特别长、列表特别空时页面不散架。

完成标准：四项逐项检查过，用户在手机和桌面宽度下都看过最终页。

## Skill 联动（只路由，不重复）

| 时机 | 路由到 |
|---|---|
| Step 1 用户意图本身模糊（连用途都说不清） | `brainstorming` |
| Step 1 风格方向拿不准（用户只会说感受词） | `aesthetic-translator`（输出直接填方向卡） |
| Step 1/3 需要成体系的风格与设计系统决策 | `frontend-design` / `ui-ux-pro-max` |
| Step 2 用户拿不准某个模块该长什么样，先验证再写码 | `prototype`（丢掉式原型回答设计问题） |
| 完成后用户要求审查 | `code-review` |

本 skill 只负责模块化陪建流程本身；被路由的 skill 输出结果后**回到本流程继续**。
