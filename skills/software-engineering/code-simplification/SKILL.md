# code-simplification — 代码与项目「做减法」

用证据找出并移除不必要的复杂度，让系统更容易理解、验证和修改，而不是单纯压低代码行数。

详细场景、判断依据和可选的「减法分析报告」格式见 [references/subtraction-playbook.md](references/subtraction-playbook.md)。

## 触发与边界

- **适用**：定位死代码或无用的依赖、合并或清理重复逻辑、拆掉多余的抽象层、评估下线旧功能/旧接口，以及获得授权后实施这些删减。
- **不适用**：没有明确减法目标的常规架构或结构重构；纯概念提问直接回答即可。
- **操作边界**：只做分析时不改代码；只有本次任务授权删除或修改时才动文件。每次尽量只做一项可独立理解的删减，不混入无关重构。

## 核心原则

- **没有引用不等于可删**：先查入口配置、反射或动态调用、插件注册、生成代码、运维脚本和实际运行路径。
- **重复是调查信号**：只有合并后能减少知识重复，且不会显著增加耦合、跳转成本或性能负担时才抽象；如果抽离后要跨多个文件跳来跳去才能看懂一条简单流程，保留局部清晰的实现。
- **复杂度按维护与变化成本判断**：是否多余取决于需求、调用方、变化方式和验证代价，不由行数或“重复几次就必须抽”决定。

## 执行步骤

### 1. 定目标与授权

确认用户要的是减法分析建议，还是已经授权实施删除；确认受影响的功能与调用方，以及不应改变的行为、兼容性和性能要求。若只是概念性提问，直接解释即可。

### 2. 收集候选项证据

检查候选项的引用关系、入口配置、动态调用、生成代码、插件约定、运行路径和维护历史，使用项目现有的静态分析、依赖检查、文档和验证手段。把观察到的现成事实与推断分开；仅凭搜索无引用或一次未执行，不足以证明可删。

### 3. 按影响与证据分级

综合影响面、可逆性、兼容性、性能要求和证据质量。风险级别用于沟通，不是删除门槛：

- **低**：局部、易回滚、用途清楚，现有静态检查足以支持判断。
- **中**：涉及内部边界、配置或多个调用方，需要更完整的调用链、构建或行为验证。
- **高**：公共 API、线上功能、数据/安全边界或性能关键路径；先确认依赖方、迁移与回滚方案，必要时分阶段弃用。

证据不足时说明缺什么证据或建议暂缓，不盲删；没有测试既不自动代表不能删，也不代表可以盲删，按风险补足针对关键行为的检查。

### 4. 给出建议或做最小删减

每个候选项写清位置、为何可能多余、建议动作（删除/合并/内联/暂缓）、影响和验证方法。获得授权实施时按最小改动落盘。

### 5. 按影响验证并汇报

遵循项目的验证约定，选择与影响相称的静态检查、构建、测试、接口兼容或性能对比。消融对照只用于风险较高、行为影响不明或现有证据不足的候选项：在隔离且可回滚的环境中一次移除一个候选项，复现基线并比较结果。结果无差异只支持当前验证范围，不证明所有配置、未来需求或未覆盖路径都不受影响。

分析任务可按 playbook 中的可选报告格式输出。

## 谨慎处理的情况

公共 API、跨服务功能、数据迁移、错误处理、安全边界和性能关键代码，先分析兼容性和失败后果，再选择渐进式弃用或加强验证。线上或共享变更按项目流程写清影响、备份/回滚和观察方式；普通本地清理不必机械套用发布流程。
