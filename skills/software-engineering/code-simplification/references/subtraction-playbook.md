# 减法场景手册

本手册补充 [SKILL.md](../SKILL.md) 的判断流程，提供候选项检查、验证方式、研究依据和可选报告模板。按当前场景查阅即可。

## 代码层面

### 死代码与未使用声明

- 未使用的 import、局部变量、私有函数：先用语言工具和全仓引用检查确认。
- 看似不可达的代码：检查反射、动态注册、插件发现、序列化名称、生成代码、脚本入口及外部调用约定。
- 注释掉的旧实现：确认不是文档示例、迁移说明或生成输入后再移除。版本控制可以追溯文本，但不能替代对行为的判断。

常见工具包括 ESLint/Pyright、编译器告警、IDE 引用查询、`go vet`；按仓库实际配置使用，不为一次清理安装新依赖。

### 重复逻辑

先判断重复的是同一条业务规则，还是碰巧相似、未来会独立变化的实现。合并可减少同步修改和不一致风险；也可能增加参数、间接跳转、调用方耦合或性能成本。评估修改后的调用上下文是否更容易理解，再决定保留重复或提取共同实现。

```python
# 两段逻辑的规则一致、变化也应同步时，可考虑提取

def validate_user(user):
    validate_fields(user)
    save(user)


def validate_admin(admin):
    validate_fields(admin)
    save(admin)
```

不要仅因重复达到某个次数就抽象。若抽象让读者必须在多个文件间跳转才能理解简单流程，保留局部重复可能更清楚。

### 条件与控制流

卫语句可以减少不必要的嵌套，但要确认空值、异常、日志、清理动作和返回值语义不变。改动前后应覆盖原本重要的分支；不要把格式更短当作逻辑等价的证据。

```javascript
function process(data) {
  if (!data || !data.valid || data.items.length === 0) return;
  return doWork(data);
}
```

### 抽象与模块边界

审查接口、包装层和小函数时，检查它们隐藏了什么变化、是否承载独立概念、是否隔离外部依赖，以及删除后哪些调用方会直接依赖实现细节。只有一个实现或一个调用方可以作为线索，不能单独决定删除。

## 依赖层面

先确认依赖是否用于运行时、构建、测试、插件发现或可选平台，再查看仓库锁文件、包管理器和实际导入路径。能否用标准库替换，还要比较平台支持、行为差异、性能和维护负担。

```bash
npm:   npx depcheck
maven: mvn dependency:analyze
go:    go mod why <package>
python: deptry <project>
```

工具的未使用报告可能漏掉动态加载或外部入口；移除前核对仓库约定和运行方式。不要为了清理单个依赖而未经验证地替换 API。

## 模块与服务层面

合并或下沉模块前，检查：

- 是否由相同调用方使用，是否频繁一起变化；
- 边界是否隐藏可变决定，还是只增加一次跳转；
- 合并是否扩大故障影响、权限范围或部署耦合；
- “无人使用”是否只代表某个环境或时间段。

单实现接口、单调用服务或长期未见调用，都是调查入口，不是自动删除条件。跨团队、线上或公共边界按高影响变更处理。

## 验证方式

按变更影响选择最小充分证据，并遵循仓库验证政策：

- **静态证据**：引用/依赖搜索、类型检查、lint、包管理器分析；适合确认局部声明和显式依赖。
- **构建与测试**：相关单元、集成、端到端或契约检查；验证已覆盖路径的行为。
- **运行/性能对照**：适用于运行时可达性、资源使用或性能关键实现；确保基线与候选版本使用相同输入和环境。
- **消融对照**：在影响较高或静态证据无法判定时才采用。使用隔离、可回滚的工作环境，一次移除一个候选项，记录基线、输入、输出和限制；若发现差异，先恢复，再判断其真实用途。

任何单一检查都有边界。测试未失败仅说明这些测试和输入未暴露差异；静态分析也可能遗漏反射、运行时配置或外部集成。报告里说明验证覆盖了什么、没覆盖什么。

## 高影响删除

适用于公共 API、线上功能、共享服务或兼容性承诺：

1. 只读确认调用方、使用版本、运行入口和迁移依赖。
2. 与项目负责人确认弃用信号、迁移替代方案、版本周期和回滚条件。
3. 按项目发布政策标记弃用并通知受影响方；观察时间由实际发布节奏和风险决定，不设统一周数。
4. 在可回滚发布中观察相关错误、使用和性能指标；出现预设回滚条件则恢复或暂停删除。
5. 删除后同步清理对应的内部测试、注释和文档；保留证明行为或兼容性要求的材料。

## 理论与实证依据

这些来源为决策原则提供依据，不构成对具体代码可删的证明，也不意味着代码越少越好。

- **软件收缩与依赖传播**：Parnas 将软件设计为易扩展、易收缩视作面向变化的问题，讨论移除功能子集时，分散的依赖和组件假设会增加收缩成本。这支持先分析依赖传播和可移除性，而非以减少行数作为成功标准。论文是基础设计论述和示例，不是对所有现代项目的受控实证评估。[论文 DOI](https://doi.org/10.1109/TSE.1979.234169) · [原文 PDF](https://users.ece.utexas.edu/~perry/education/SE-Intro/parnas.pdf)
- **去重的上下文权衡**：2026 年 ACM/IEEE Technical Debt 论文分析 Linux 内核两个子系统的去重补丁评审。研究记录了维护者因可读性、跨位置跳转、集成成本或性能考量而修改或拒绝部分去重方案。这是特定项目和评审情境的定性研究，不提供适用于所有代码库的统一抽象规则。[论文 DOI](https://doi.org/10.1145/3794915.3795783)
- **测试轨迹的局限**：2026 年 arXiv 预印本以 11 个程序的人工裁剪版本为 ground truth，评估自动代码裁剪工具；作者报告测试驱动方法可能删掉测试未触发但仍必要的错误处理和线程同步代码。该研究针对自动 debloating，不能直接量化人工删除的风险；它支持把测试结果视为证据之一，而非完整行为证明。[论文与全文](https://arxiv.org/abs/2604.17717)

证据适用时，应优先用它解释“为什么需要检查依赖、权衡可读性、说明验证边界”；不要把上述论文扩写成“任何删除都必须消融”或“抽象通常有害”等来源未证明的结论。

## 减法分析报告（可选）

简短问答、低风险单点建议或用户已要求直接实施时，不必输出完整报告。需要逐项审阅时可使用：

```markdown
## 减法分析报告

### 扫描结果（共发现 N 处）

| 编号 | 层次 | 位置 | 候选问题 | 风险摘要 |
|------|------|------|----------|----------|
| 1 | 代码/结构/依赖/功能 | ... | ... | 低/中/高及原因 |

### 逐项分析

#### #1：[简短标题]
**证据**：引用、调用链、配置或运行观察；注明未知项。
**判断**：为什么可能多余，以及保留/删除的维护代价。
**建议**：删除 / 合并 / 内联 / 暂缓，并给出最小改动。
**验证**：基线、检查或测试结果；必要时说明消融对照和覆盖边界。
**影响与回滚**：兼容性、调用方、发布要求和恢复办法。

### 结论

按优先级列出可执行项、待补证据项和建议保留项。
```
