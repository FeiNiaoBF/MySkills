# 案例与验收情境

前面的情境用于检验规划和路由判断，不是默认目录模板，也不代表行为已经通过；标为“真实”的案例记录特定 Skill 版本和模型的一次隔离验证，不能外推为所有模型都稳定通过。评估时先依据输入独立工作，再对照预期；路径可随项目约定调整，职责和证据边界必须成立。

目录树只列文档，省略代码及其他无关文件。规则依据见 [规划规则](planning-rules.md)。

## 1. 只有初步项目定位，没有代码

**输入：**新仓库已有一段初步定位，用户希望协作者能理解项目；没有确认的功能清单、运行方式或技术选择。

**规划：**保留已有定位及其初步状态。创建精简 README，说明用途、当前阶段和已知边界；不扩写成需求规格、技术设计、架构或操作指南。

```text
README.md
```

**验收：**读者知道项目想解决什么问题以及尚未实现；没有安装命令、功能承诺或假想技术决策。若只是个人临时构想且用户没有要求持久记录，可以不创建任何文件。

**分支：**用户要求整理上游工具已确认的讨论时，以 `project-brief.md` 替代上面的 README，保留有来源的目标、受众、边界和未决项。不重启访谈，不额外创建 README、Requirements 或 Architecture；已有同职责简报则更新。

**理由：**介绍项目或交接已确认结论有真实用途，但其他文档尚无证据和独立职责。

## 2. 完整 Go CLI，没有文档

**输入：**代码、测试和 `--help` 存在；命令帮助已覆盖参数。读者需要安装并完成一次基本任务，没有已知的复杂操作场景。

**规划：**保留帮助及测试作为证据。创建 README，依据构建配置、发布信息和运行结果提供适用的安装或构建方式、最小示例、结果和帮助入口。不要仅根据模块名猜测存在发布包或可用的安装地址。

```text
README.md
```

**验收：**安全条件下实际运行示例；未执行则明确验证限制。README 引用命令帮助，不复制完整参数表；不从实现反向编造 Requirements 或历史 ADR。

**分支：**发现配置优先级或复杂格式不能由帮助充分表达、读者又需要独立查阅时，增加 `docs/configuration.md`；若已有生成器则维护生成源和导航，不手写第二份参考。

**理由：**缺少的是可用入口。项目语言和代码规模不能独立证明需要 Reference、Architecture 或 Tutorial。

## 3. README 冗长且混乱

**输入：**README 混合了仍有效的起步示例、重复介绍、已失效命令和只有贡献者才需要的测试发布流程；贡献流程需独立维护。

**规划：**保留准确定位和起步信息，按读者路径重排；依据证据纠正过时命令，删除无用重复。将贡献流程迁入 CONTRIBUTING，README 留入口；维护已知旧锚点的引用。

```text
README.md
CONTRIBUTING.md
```

**验收：**按 [执行入口的写作质量检查](../SKILL.md#5-验证与交付) 对照修改前后：必要环境、安装/运行命令、支持范围、数据风险、失败处理和既有链接不能因精简丢失；移出的信息须有有效入口。首次使用者不必穿过发布细节才能运行项目；贡献者能直接找到完整流程。若输入实际只有顺序混乱和重复，整理一个 README 即可，不必拆分。

**理由：**此处分离由读者任务和维护责任驱动，与篇幅无关。

**阅读质量变体：**README 虽长，但每节都包含必要条件、兼容限制或异常处理时，不以缩短为目标；结构清楚且信息充分时允许保留原文。README 很短但读者无法理解或开始使用时，按项目证据补足背景、解释和示例；篇幅增加不影响验收。

## 4. 需求与技术设计大量重复

**输入：**`docs/requirements.md` 的已确认验收条件被 `docs/design.md` 全量复制；需求供两个实现使用，技术设计只针对其中一个实现。

**规划：**保留两份文档。需求和验收条件继续由 requirements 维护；design 删除完整副本，使用必要摘要、需求链接及实现方案。设计中独有的有效约束须先辨认归属，再迁移，不能直接删除。

```text
README.md
docs/
  requirements.md
  design.md
```

**验收：**修改一项需求不再要求手动同步完整副本；设计仍能解释如何满足需求；两份文件的状态和范围明确。

**合并分支：**若输入改为同一小功能、相同评审者和生命周期，则合并为 `docs/import-design.md`，用“目标与验收”“行为规格”“技术方案”章节保留职责。同步旧引用，按项目约定处理旧文件。

**理由：**重复要求去重；是否合并取决于独立维护需求。

## 5. 多模块应用，架构复杂且有重要决策

**输入：**API、任务调度和存储模块相互依赖；已有模块 README，内容有效。团队有可核验的“使用持久队列解耦任务”决定及评审理由，跨模块故障传播难从局部文档理解。

**规划：**保留根入口和模块说明。创建 architecture，描述系统边界、职责、关键运行链路及故障影响；为已有重要决定记录 ADR 并引用评审证据，不补造未讨论过的备选方案。不因多模块自动创建需求、指南或参考目录。

```text
README.md
docs/
  architecture.md
  decisions/
    0001-use-durable-queue.md
modules/
  api/README.md
  scheduler/README.md
  storage/README.md
```

**验收：**architecture 解释模块之间的关系，模块 README 负责各自局部内容；ADR 解释当时的决定，架构概览不复制整份理由。若无法确认决定背景，只写可验证的现状，把背景作为缺口，不生成 accepted ADR。

**理由：**系统视图与决策历史有独立用途；既有局部文档保持权威。

## 6. 实现与已确认需求不一致

**输入：**已确认需求规定导入失败时不得留下部分数据；当前指定版本的运行证据显示发生部分写入。README 声称导入是原子的，既有 `docs/import-spec.md` 定义目标契约。

**规划：**保留 import-spec 的已确认要求。纠正 README 中对当前能力的错误承诺，注明受影响版本的限制和规范入口。报告实现偏差及证据，在已有缺陷追踪流程中继续处理；若外部建单未获授权，先交付可建单的差异描述。

```text
README.md
docs/
  import-spec.md
```

**验收：**需求仍为原子导入；用户能知道当前限制；没有把缺陷包装成新的既定设计。未确认安全的绕过方法不能写成建议步骤。无需新建冲突文件、ADR 或架构文档。

**理由：**预期契约与当前行为都需要准确表达，文档维护不能擅自改变产品决定。

## 7. 新项目分阶段完善

**输入：**第一轮只有上游探索已经确认的项目目标与范围，用户要求整理为简报；第二轮提供可运行的本地导入工具和帮助信息，要求补齐使用文档；第三轮提供新增预览能力的代码变更。

**规划：**第一轮只创建 `project-brief.md`，保留已确认结论和未决项。第二轮创建 README，说明有证据支持的起步步骤、结果与限制，并链接简报中的项目范围。第三轮更新 README 中相关用法和示例；若内容没有独立阅读或维护用途，仍保留现有结构。

```text
第一轮：
project-brief.md

第二轮及第三轮：
README.md
project-brief.md
```

**验收：**每轮产物都解决当前读者任务；没有在第一轮虚构运行命令，也没有在后续重写已确认目标、丢弃有效说明或生成空的 Architecture、ADR、进度文件。实际执行可安全运行的示例，未执行项如实说明。

**理由：**文档随可用信息和项目能力发展；本例中简报维护项目范围，README 支持使用，两者职责可辨。其他项目若没有这种独立用途，可以在同一权威文档中逐步完善。

## 8. 共同打磨与工作方式切换

**输入：**用户说“陪我梳理 README，先讨论用途和起步部分，不要写文件”，材料中已有准确定位和可运行示例，支持平台尚未确认。

**规划：**依据已有材料在回复中给出该部分的草稿，只询问影响内容判断的问题，不展开整套需求访谈，也不因平台未知而搁置全部内容。根据反馈修订；用户授权写入当前部分后，才更新 README。若随后要求“其他部分你直接补齐”，切换为直接完成其余已授权内容。

**验收：**讨论阶段文件不变；授权后只修改约定范围，保留已确认段落；缺证据的平台支持不写成承诺。用户只要求规划或审查时，也不会因默认直接完成而自动改文件。

**理由：**工作方式决定协作节奏，用户授权决定落盘范围；两种方式使用相同的证据和质量要求。

## 9. 有界评估与文档维护

**输入 A：**用户说“评估这份 ADR 是否足以支持迁移决定，不要修改文件”。

**处理：**主要产物是只读判断，不启动文档编写或维护流程；根据 ADR 的用途给出证据化结论和未知项，不改写或建立配套文档。

**输入 B：**用户说“检查这份 ADR，并把缺失的背景、取舍和后果补齐”。

**处理：**审查是维护工作的组成部分；先核对决定状态和来源，再在授权范围内修订。若缺少只有决定者才能确认的信息，只完成不依赖它的部分并提出具体缺口。

**验收：**主要产物是判断时不写文件；主要产物是有依据的文档修订时不只停留在评分或泛化建议。两种情形都不自动组织额外工作流。

**理由：**处理方式由用户要得到的主要产物决定，而不是由“评估”“审查”这类共享动词决定。

**行为验证：**2026-10-21 在无写入工具的新会话中，以仓库中的 ADR 0003 执行输入 A。模型只给出有证据状态的判断和未知项，没有进入文档改写或治理规划。该结果只证明这一模型和案例的边界表现。

**设计文档边界变体：**若主要内容是项目需求、行为规格、内部技术设计、系统架构或 ADR，使用本文档工作流；若主要内容是 UI 视觉语言、设计令牌、组件用法、变体和状态，则属于独立的 UI 设计文档任务。不要仅凭文件名 `DESIGN.md` 判断。文档同时引用两类信息时，各自在权威位置维护，使用必要摘要和链接连接，不复制完整规则。

**设计文档边界验证：**2026-10-21 在无写入工具的新会话中测试四个案例。模型把名为 `DESIGN.md` 的服务边界、队列方案和 ADR 文档判为项目技术文档，把非 `DESIGN.md` 的 UI 令牌与组件状态文档判为独立 UI 设计文档；两个混合案例都按主要读者任务确定范围，并只引用另一类信息的权威位置。

## 10. 真实维护案例：校验器范围扩大

**来源：**MySkills 提交 `2db51b1` 将 `scripts/validate-video-skills.py` 从视频 Skill 专用校验器改为兼容入口，并新增 `scripts/validate_skills.py` 作为全仓库校验器；变更前 README 仍将旧命令描述为只检查视频 Skill。

**任务：**依据变更后的脚本和依赖文件，维护 README 的验证说明，保留不受影响的安装与使用内容。

**预期：**把首选命令、全仓库覆盖范围、依赖安装、兼容入口和检查限制写清；包含命令围栏的候选 Markdown 可直接复制并正确渲染；不把测试通过表述为语义质量已经验证，不借机重写整个 README，也不创建验证治理文档。能安全执行时运行新命令，并记录实际结果。

**无修改分支：**如果变化只是校验器内部重构，命令、覆盖范围、依赖、输出和读者操作均未改变，则文档无需更新。

**理由：**这是由读者可见行为变化触发的局部维护；检查范围沿权威说明、命令示例和入口导航展开，而不是按文件数量扩张。

**行为验证：**2026-10-21 使用源码版 `project-docs` 0.5.0 和 `magpie/codex/gpt-5.6-sol` 在无写入工具的新会话中重放该提交。首次输出正确限定修改范围和事实，但用三反引号外层包住内部命令围栏，候选 Markdown 无法直接复制；据此补充围栏规则后复测，输出改用四反引号外层，保留旧段落、修订正文、证据和未验证项均完整。另在该提交的完整临时快照上实际运行校验器，得到预期的 `FAIL` 格式和两个当时已存在的问题；模型没有把静态核对声称为运行通过。

## 11. 真实生成案例：仓库校验器说明

**来源：**当前 MySkills 的 `scripts/validate_skills.py` 和 `requirements-dev.txt`，不提供已有 CONTRIBUTING 或 README 作为答案来源。

**任务：**为已经克隆仓库且能够运行 Python 的贡献者生成“运行仓库校验器”小节，说明安装依赖、首选命令、成功与失败信号、覆盖范围和主要限制；证据不足的内容不写。

**预期：**读者能够按顺序安装依赖和运行校验；能够辨认成功、失败和缺依赖；知道静态检查覆盖什么、不能证明什么。不得编造 Python 版本、单元测试、CI 或操作系统支持。

**行为验证：**2026-10-21 使用源码版 `project-docs` 0.5.0 和同一模型在无写入工具的新会话中生成。输出正确给出依赖安装、默认命令、可选 `--root`、退出状态、覆盖范围和静态检查边界；明确列出因证据不足而未写入的 Python 版本、测试和 CI 信息，也没有声称命令已经执行。对照源码未发现会改变读者操作的事实错误。

## 评估方法

这些情境可用于人工推演；真实行为评估需要在隔离样例中实际调用 Skill，保存实际加载的 Skill 版本与来源、输入、生成结果和验证证据。每次改变本 Skill 的写作或维护行为，至少使用一个真实项目的生成任务和一个真实变更的维护任务；实际代码、文档和版本历史作为输入，合成变体只能补充边界。优先在未接触预期答案的新会话中执行，再对照验收条件；同一会话执行与自评时明确局限。不能把文档检查、本页预期或模型自述当作行为通过。

结果可放在系统临时目录或项目已有评估位置；不要仅为记录一次运行建立新的治理目录、评分系统或长期同步清单。

对每次结果检查（写作质量和语言以 [执行入口](../SKILL.md) 为准，此处不重复规则）：

- 新建文件是否有输入事实支持的独立职责，而非仅套用示例目录？
- 读者能否从入口找到、理解并使用所需信息？必要背景和关键内容是否因“精简”被遗漏？
- 权威信息、摘要、生成内容与历史材料是否区分清楚？
- 输出是否保留已确认需求、现有约定和用户修改，明确未知及未执行项？

隔离样例至少覆盖：真实材料生成文档、真实变更维护文档、仅规划项目简报（不写文件）、共同打磨到直接完成的切换、改进冗长 README、只读判断与文档维护的边界、仅审查含错误的技术文档和指南（不改文件）、维护与实现冲突的说明（不改已确认需求）。各样例保存任务、源材料、处理前后文件清单及内容；改写前列出重要信息，完成后逐项验证去向，并实际执行可安全运行的示例。语言至少检查用户指定语言覆盖项目语言、未指定时沿用项目语言两条分支。记录检查结果及未执行项，不以预期答案冒充产物。

边界变体：已有外部文档站时保留其权威位置；很久未修改但仍正确的文档不判为过时；历史 ADR 不因实现已改变而删除；项目只授权审查时不写文件；相似项目的版本、配置或能力不同，输出必须依据各自材料。这些变体检验规则能否随事实改变结论。
