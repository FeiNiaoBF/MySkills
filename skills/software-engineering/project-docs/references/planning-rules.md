# Documentation Planning Rules v0.3

## 1. 从信息到文档

必须按以下顺序判断，不从目录模板开始：

1. **识别任务：**谁需要这项信息，用来做什么，缺失会造成什么障碍？读者需要、交接需要和项目明确的留存要求都可构成记录理由。
2. **核对证据：**确认信息描述当前实现、预期行为、已确认决定还是未决方案，并限定版本、范围和来源。
3. **判断记录价值：**信息是否需要持续查阅、解释、执行或追溯？没有则不记录。能从代码推导不等于无需文档；读者无法便捷理解时，提供解释或可读的生成视图。
4. **寻找权威位置：**现有文档、代码注释、Schema、问题跟踪或文档站能否承担它？可以则更新或链接；同一事实与适用范围只保留一个权威维护位置。
5. **判断独立性：**能否用现有文档的一个清楚章节满足任务？若可以，先不拆分。若不行，具体指出是阅读任务分离、信息关系复杂，还是维护周期独立。
6. **选择动作：**按下表决定更新、创建、合并、拆分、保留或不记录。随后选择路径，并核对引用和验证方式。

独立文档必须同时满足：有明确读者或留存用途；有足以支撑该用途的信息；有可指出的独立阅读或维护收益；有可发现的入口和维护来源。无需统一配置负责人字段，但要知道什么变更会使内容失效。

“复杂”指读者需要同时理解多种关系、分支、前提或视图，不能靠局部整理消除阅读障碍。不同维护者、版本范围、审批权限或更新节奏也可构成独立理由。以上是定性判断，不设字数、文件数或打分阈值。

## 2. 信息职责映射

职责可由文件、章节、生成页面或已有外部系统承担；本表不是创建清单。

| 信息 | 回答的问题 | 典型承载位置与独立条件 |
| --- | --- | --- |
| 项目定义 | 做什么、面向谁、边界是什么？ | 默认 README；项目定位需跨产品复用或独立评审时才独立 |
| Requirements（需求） | 必须满足哪些用户目标、业务约束和验收条件？ | README 的范围、功能文档或既有需求系统；跨功能、团队或版本维护时独立 |
| Spec（规格） | 外部可观察的行为和契约具体是什么？ | 功能文档、协议规范或 Schema；存在独立消费者、兼容性或一致性验证要求时独立 |
| Technical Design（技术设计） | 用什么内部结构、算法和迁移方案实现？ | 功能文档中的技术方案；独立评审或演进时独立。不得复制需求和接口契约 |
| Architecture（架构） | 系统边界、模块职责和关键交互如何组成整体？ | 简单项目在 README 说明；跨模块、运行或部署关系难以局部理解时独立 |
| ADR（决策记录） | 为什么在当时条件下作出这一重要选择？ | 跨模块约束、重要质量取舍或难以逆转的选择值得记录；每条一个决定，保留背景、选择、后果和状态，不复写整份设计 |
| Tutorial（教程） | 初学者如何通过一条实践路径学会使用？ | 有真实学习任务和可验证路径时创建；简短起步可在 README |
| How-to / Guide（操作指南） | 已有目标的读者如何完成具体任务？ | 前提、步骤、结果；分支、角色或环境复杂到需要独立查阅时独立 |
| Reference（参考） | 参数、配置、API 或格式准确是什么？ | 优先使用帮助、注释或 Schema 的生成视图；独立查阅需求成立时提供页面 |
| Explanation（解释） | 某个概念或机制为什么如此工作？ | 就近解释；独立理解任务成立时单列。Architecture 是系统层面的解释之一 |

Diátaxis 的学习、操作、查阅和理解用于识别阅读任务。不要为了四个类别预建目录，也不要把 ADR、需求和规格强制归入四个用户文档目录。

### Requirements、Spec、Technical Design 的边界

- **建议合并：**围绕同一功能、读者连续阅读、范围和维护周期一致时，放在一份功能文档，用章节区分目标及验收、行为契约、实现方案。职责不同不必对应不同文件。
- **必须保留独立权威：**契约供多个实现使用、需求由独立流程批准，或设计可被替换而需求不变时，不把这些信息混为一份可随意改写的描述。可以分文件，也可以在同一文件中明确受独立控制的章节，沿用项目流程。
- **建议拆分：**独立评审、权限或版本范围使同文件维护产生实际摩擦，或读者经常被无关内容打断时，分开维护并链接。
- **重复先去重：**重复的需求和契约保留在各自权威位置。两份文档有重复，不足以证明应该合并。
- **注意生命周期：**评审中的方案标为提案；已实现的设计按项目约定成为历史记录或持续维护的设计说明，必须说清用途。不能把历史方案当作当前实现手册。

## 3. README 与独立文档

README 默认承担项目入口：定位、当前可用状态、最短可行起步路径、关键限制、帮助和深入阅读入口。按已有信息填写，不给没有代码的项目编造安装步骤或功能承诺。

**留在 README：**首次访问者共同需要的信息，以及能直接支持起步的简短说明和示例。重要限制即使详述在别处，也应在相关入口摘要提示。

**移出 README：**只服务特定角色或任务的完整流程、需要系统查阅的接口细节、独立维护的设计或决策，且独立收益满足第 1 节条件。移出后保留足够定位信息和链接；不要把 README 清空成无上下文的链接列表。

**保留现状：**调整顺序、标题、重复和陈旧内容已能解决问题时，保持一个 README 即可。长不是拆分理由，短也不意味着适合合并。

已有有效的文档站、模块入口或用户指定范围时不强制从 README 开始；入口最终应能指向相关信息。

## 4. 动作判断与审查信号

| 动作 | 条件 | 必须检查 |
| --- | --- | --- |
| 更新 | 职责正确，信息缺失、过时或难读 | 证据支持修改；未把目标改成现状 |
| 创建 | 有持续用途，现有位置无法充分承担，独立收益明确 | 内容、入口和维护来源齐备，无空模板 |
| 合并 | 同一读者任务和生命周期，分开造成重复维护或跳转 | 不丢独有约束、验收条件、决策历史和引用 |
| 拆分 | 独立任务或维护边界带来具体收益 | 各文档可理解、导航连续、权威内容未复制 |
| 保留 | 信息有效，或有明确历史、留存价值 | 历史材料标明适用范围并指向当前说明 |
| 不记录 | 无持续用途、无新增价值的副本、一次性推演 | 未漏掉理解、交接或合规必需的信息 |
| 删除或归档 | 已确认失效且无当前用途 | 留存要求、独有信息和已有引用；按项目授权执行 |

审查时按事实和职责比对，不按措辞相似度直接删除：

- **重复：**同一范围内的参数、约束或行为在多处被完整维护；有来源链接的摘要、示例和生成视图不自动算重复。
- **过时：**与适用版本的实现或后续确认记录冲突，入口失效、命令无法使用、状态被替代。修改日期久远只是线索，不能独立证明过时。
- **职责重叠：**多个文件回答同一任务，却说不清应改哪一份；或同一文件交替陈述目标、提案和现状而不标状态。
- **历史记录：**过去决定与当前实现不同可能完全合理。保留其历史语义，链接替代决定或当前文档，不“修正”历史使其看似从未变化。

## 5. 命名与渐进扩展

必须先检查现有项目和生态约定、文档发布配置、链接及留存要求。结构不符合本规则的示例不等于有缺陷；只有可证实的阅读或维护问题才提出迁移。

建议沿用最浅且可发现的目录：小项目只需 README；内容独立后选描述任务或主题的文件名；出现有用分组时才建目录。多模块项目只给有独立读者或维护职责的模块增加入口，不逐目录生成 README。

优先保留 `README.md`、`CONTRIBUTING.md`、既有 ADR 命名等约定。`DESIGN.md` 在不同生态中含义不同：先确认它表示技术设计还是视觉设计规范，不覆盖既有含义。无统一标准的 Requirements、Spec 等文件名沿用项目术语，不声称平台强制要求。

索引只负责导航，不复述完整内容；文档站已有导航时不另造索引。公开路径迁移需要考虑重定向或过渡链接。仓库内部引用优先使用相对链接，跨版本契约按项目发布规则链接。

每次任务只修受影响的权威内容、摘要和入口；新增前检查能否归入已有职责，完成后检查有无残留副本或空壳。停止条件是读者任务已被充分支持，不是模板已填满。

## 6. 证据与冲突

必须先比较版本、部署环境、范围和记录状态，排除不同适用条件造成的表面冲突。不存在适用于全部信息的“代码 > 需求 > 文档”排序。

| 信息状态 | 可用证据 | 不得推断 |
| --- | --- | --- |
| 当前实现 | 相关代码、配置、测试和实际运行结果 | 存在代码等于部署已启用；测试通过等于满足全部需求 |
| 已确认需求 | 经确认的需求、验收条件或正式契约 | 当前未实现等于需求已取消；代码行为自动成为规范 |
| 已确认决策 | 有状态的 ADR、评审记录或明确确认 | 看见技术选型就能反推出决定者、理由或备选方案 |
| 未决方案 | 提案、讨论、开放问题 | 讨论过等于已接受；建议等于现有能力 |

冲突处理：

1. 记录冲突双方、来源、适用范围、影响的读者任务及最小待确认问题。规划阶段在回复中说明即可。
2. 只修改已能确认错误的描述。需求继续说明预期行为，用户文档如实描述已验证的当前限制；通过链接说明二者关系，避免形成两个互相矛盾的承诺。
3. 需要改变需求或接受方案时，请有权决定的人确认，不替他们作产品或架构决定。继续不依赖该决定的文档工作。
4. 需持续追踪的缺口沿用现有问题系统或相关文档，不默认新建冲突清单。无明确负责人时标记待分派，不因此丢弃重要问题；外部建单遵守授权。
5. 已接受 ADR 被新决定替代时，保留旧记录并关联替代记录。待定重大决定可按现有流程使用 proposed ADR，但只有真实确认后才能改为 accepted。

证据不足时缩小表述范围，注明未验证或留待确认。只有初步定位也可以写明确标注阶段的介绍；不能用空的 Requirements、Architecture 或 ADR 假装信息已齐全。

## 7. 参考依据与适用边界

以下支持规则设计，日常执行无需联网通读。这些来源没有共同规定一套目录结构；本规则是针对项目文档维护的综合判断。

- [Diátaxis](https://diataxis.fr/)：按学习、执行、查阅、理解组织文档需求。
- [arc42 概览](https://arc42.org/overview)：按需选择架构视图，不要求填满全部章节。
- [Google Documentation Best Practices](https://google.github.io/styleguide/docguide/best_practices.html)：最小可用文档、随代码更新、清理失效内容、人类优先，以及区分历史设计与当前说明。
- [Google Developer Documentation Style Guide](https://developers.google.com/style/highlights)：清楚用词、主动表达、条件先于指令、可读的链接和操作步骤。中文写作采用其清晰性原则，不照搬英文语法。
- [GitHub：About READMEs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)：项目入口与相对链接约定，不规定所有文档的文件名。
- [ADR 实践](https://adr.github.io/)：记录单个重要决定及理由、取舍和后果；遵循项目已有状态流程。
- [ASD-STE100](https://www.asd-ste100.org/)：受控技术英语的参考。这里只借鉴术语一致、表达明确的方向，不宣称符合标准，也不把英文词表或句长规则应用于中文。当前规则未依据完整标准逐条核验。
