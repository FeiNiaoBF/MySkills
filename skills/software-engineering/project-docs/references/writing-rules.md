# 写作规则：让人能读懂、能执行

从 [project-docs](../SKILL.md) 拆出的按需参考；写或改写任何项目文档时读。这里的“必须”是执行约束。

## 1. 目标与适用语言

文档首先是给人读的。写作规则服务于三个结果：读者能判断、能执行、能维护；不是让句子显得“高级”。

- **英文文档：**按 Orwell 六原则和 ASD-STE100 的写作规则执行。
- **中文文档：**执行等价原则：短常用词、主动语态、一词一义、删冗余、条件先于动作、一句一个主要意思。不要机械套用英文词表、英文句长或冠词规则。
- **其他语言：**沿用项目语言习惯，应用同一组清晰性原则；代码标识符、命令、协议名和 API 名不翻译。
- **不声称符合标准：**没有逐条对照标准与词典核验时，不写“符合 ASD-STE100”或“通过 STE 认证”；可以写“按 STE 原则写作”。

## 2. Orwell 六原则

来源：George Orwell, “Politics and the English Language”（1946）。以下是执行转述，不是原文引用。

1. **不用陈腐的比喻、明喻或其他修辞。**能用直说就不用比喻；比喻只在它能消除歧义时保留。
2. **能用短词就不用长词。**优先具体、常用、读者认识的词，不用“进行”“实现”“加以”等空壳动词堆出长句。
3. **能删的词就删。**删开场白、重复结论、装饰性形容词和没有信息的过渡句；不删条件、例外、数字、单位和安全信息。
4. **能用主动就不用被动。**写清谁执行、对什么执行、产生什么结果；只有执行者未知或无关时才用被动。
5. **能用日常词就不用外来语、生僻科学词或行话。**有日常等价说法时用日常说法；代码标识符、协议名和已确立术语除外。
6. **规则与准确性、自然表达冲突时，先保证不写出错误、怪异或伤害读者的句子。**不为守规则牺牲事实、条件、例外、警告或可执行性。

## 3. ASD-STE100 的核心约束

ASD-STE100 是受控技术英语标准，由写作规则和受控词典组成。下面只提炼项目文档最常用的部分，不复制标准全文，也不替代标准。

### 3.1 用词

- **一词一义。**同一个词在同一文档中只表达一个意思；同一个对象只用一个术语，不为了“变化”换同义词。
- **优先常用、单义的词。**能用“start”就不在“begin / commence / initiate”之间轮换；中文同理，不把“开始 / 启动 / 着手”混用指同一动作。
- **术语一致。**首次出现时用当前语境解释；之后沿用同一写法。缩写首次出现给全称。
- **不用地区俚语、网络行话和团队黑话。**除非它已经是项目权威术语，并在术语表或首次出现处解释。
- **英文多词名词不超过三个词。**超过时用介词拆开，例如把 `runway light connection resistance calibration` 改成 `calibration of the resistance of the runway light connection`。
- **英文按批准词性使用。**不把名词当动词、不把动词当名词；项目若要求严格 STE，使用其批准词表。
- **英文拼写跟随项目。**项目声明遵循 STE 时使用其美式拼写；否则沿用项目既有拼写，不混用。

### 3.2 句子

- **英文程序句不超过 20 词，描述句不超过 25 词。**中文不套用这两个数字，按“一句一个主要动作或主题”断句；读者需要回读才能断句时，句子仍然太长。
- **一句一个指令。**只有动作同时发生、无法拆成两个步骤时才合并。
- **指令用祈使句，描述用陈述句。**不要把“可以执行”“应被执行”写成指令。
- **条件在前，动作在后。**先写触发条件，再写要执行的动作；条件与动作之间用逗号或明确结构分开。
- **主动语态。**写清执行者；执行者确实未知时才用被动。
- **不省略必要成分。**英文不省略主语、动词、冠词，不用 `don't`、`isn't` 这类缩写；中文不省略“谁对什么做什么”。
- **避免歧义代词。**少用“它”“这个”“该”“相关”“上述”，必要时重复具体名词。
- **英文不用分号。**拆成两句，或改成竖排列表。
- **英文使用简单时态。**用一般现在时、一般过去时、一般将来时和祈使句；避免完成时、进行时和复杂助动词。
- **英文避免把 -ing 形式当动词。**只在标题、固定术语或已有搭配中使用；不要把 `when doing this` 写成进行时。
- **避免名词化。**能用动词就用动词，例如把“对配置进行应用”改成“应用配置”。

### 3.3 段落与结构

- **一段一个主题。**首句告诉读者这一段讲什么；后续句子解释、举例或给限制。
- **英文一段不超过六句。**超过时按主题拆分，不按字数硬切。
- **复杂并列改列表。**列表引导句以冒号结束，各项与引导句能直接衔接；不要把不同层级混在一个列表里。
- **先结论，后背景。**读者最需要的状态、动作或限制先出现；背景按理解依赖补充。
- **标题说明主题或任务。**不用“简介”“说明”“其他”这类不承载信息的标题。

### 3.4 操作与安全

- **步骤可执行。**写清前提、按序动作、可识别的成功结果，以及当前任务需要的常见失败处理。
- **警告先给命令或条件，再给后果。**说明不遵守会发生什么；不要只写“注意安全”。
- **说明不是指令。**NOTE 只放信息，不放必须执行的步骤、限制或容差；这些放回相关步骤。
- **破坏性操作写影响和恢复方式。**没有恢复方式时明确写出；不编造回滚步骤。
- **不把安全信息埋进长段落。**该独立成警告、注意或前置条件时，不混在普通说明里。

## 4. 按文档类型落地

| 文档 | 必须做到 | 常见违规 |
| --- | --- | --- |
| README | 先让读者判断用途与适用性，再给最小可运行路径、当前限制和深入入口 | 用愿景和形容词替代事实；安装命令没有证据；把计划写成可用功能 |
| 操作指南 | 前提、按序步骤、成功信号、常见失败处理 | 只列命令不写结果；条件放在动作后面；多个动作挤成一句 |
| 参考 | 一词一义、参数和默认值准确、完整契约只在权威位置维护 | 同义术语轮换；手写第二份完整参数表；用散文复述表格 |
| 需求 / 规格 | 可观察行为、输入输出、错误、边界、版本范围 | 把内部实现当外部契约；用“支持”“优化”等无法验收的词 |
| 技术设计 / 架构 | 边界、依赖方向、关键路径、失败影响、取舍 | 目录名清单冒充架构；只写结论不写理由；复制完整需求 |
| ADR | 问题与触发、决定、真实备选、非目标、接受代价、复访条件 | 编造备选；只写“采用了 X”；复制实施计划 |
| 教程 / 解释 | 一条可完成的学习或理解路径；术语首次出现时解释 | 假设读者已有开发者背景；用比喻代替机制；跳步 |

## 5. 写完检查

按顺序检查本轮文档；发现问题就改，不把检查写成报告：

1. **可行动：**读者能否据此判断、执行或维护，而不需要再问作者？
2. **一词一义：**同一对象是否始终用同一个术语？有没有为了“变化”换同义词？
3. **主动明确：**被动句是否说明了执行者？条件是否在动作之前？
4. **删冗余：**能否删掉开场白、重复结论、空壳动词和装饰性形容词，而不丢条件、例外、数字或安全信息？
5. **去行话：**有没有可以用日常词替代的外来语、生僻词或团队黑话？术语是否首次解释？
6. **句子可读：**英文是否超过 20/25 词？中文是否一句塞了多个动作或条件？是否需要回读才能断句？
7. **段落单一：**每段是否只有一个主题？英文是否超过六句？
8. **安全与限制：**警告是否先命令/条件、后后果？NOTE 里是否藏了指令？破坏性操作是否写了影响和恢复？
9. **保真：**简化后是否仍保留名称、数字、单位、命令、路径、链接、条件、取舍和不确定性？有没有把“可能/通常/计划”升级成“会/总是/已支持”？

## 6. 例外

以下内容不按普通 prose 简化：

- 引用文本、许可证、法律条款和必须逐字保留的原文；
- 代码、命令、配置、API 路径、协议名、错误信息和标识符；
- 已确立的行业术语、标准名称和项目术语表条目；
- 安全警告中必须保留的精确条件、数值和后果。

例外不等于可以写空话。例外内容仍要结构清楚、术语一致、条件明确；只在不改变含义的前提下简化外围说明。
