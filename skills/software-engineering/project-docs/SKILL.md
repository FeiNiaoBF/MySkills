# project-docs

根据代码、已有文档、已确认需求和讨论记录，为新项目逐步建立文档，为已有项目持续整理和完善文档。核心价值不是精确决定文件数量，而是让 Agent 基于可靠事实，写出人愿意读、能够理解、实际有用且以后能维护的文档。结构只服务于读者任务；不把目录完整、文件数量、负责人字段或例行盘点当作文档质量。

本文和参考中的“必须”是执行约束；“建议”“默认”可根据项目事实调整并说明理由。

## 职责边界

- **使用 `project-docs`：**用户要规划、编写、改写或维护项目文档，或者希望审查结果直接服务于这些文档工作。
- **使用 `assess`：**用户要判断一份指定文档是否适合其用途、比较优缺点或获得证据化结论，但没有要求继续编写或维护。`project-docs` 的审查关注文档应如何修复和保持可用；`assess` 的产物是判断。不要因同一目标可由两者触及就自动串联调用。
- **使用上游探索工具：**目标、需求或决定本身尚未形成时，交给用户或当前环境可用的 `problem-exploration`、`grilling` 等工具；本 Skill 只整理已确认结果，不代替探索或决策。
- **使用 `project-implementation-planner`：**用户要决定实现顺序、依赖和最小可交付切片。只有实施工作需要正式项目文档时，再由本 Skill 提供写作指导；文档不是规划实施的固定前置阶段。

以用户期望的主要产物选择一个主 Skill。边界不清但不会改变当前文档内容时，直接完成有依据的部分，不先组织一套 Skill 流程。

## 执行流程

### 1. 确定范围并读取证据

- 识别用户要的是规划、编写、审查还是维护，以及涉及的项目、功能和版本。结合已有材料确定主要读者、知识背景和阅读任务，不默认读者熟悉开发者已知的概念。沿用已给出的目标，不重复访谈。
- 读取适用的项目约定、文档入口和本次相关材料，再沿信息缺口检查代码入口、接口、配置、测试或需求记录。未限定单篇的项目文档任务，先从整体关系判断需要补充、更新或调整什么；局部修改只检查相关内容。新项目没有代码或文档时，从已确认资料起步，不预建完整目录。
- 每次调用依据当前材料完成有价值且有证据支持的工作；新代码、新需求或新决定出现后，核对已有文档并更新受影响部分。渐进完善不限定每次只能写一篇，也不要求首次完成整套文档。
- 先检查工作区改动，保留用户内容。仓库外的 Wiki、需求系统或文档站也可能是权威来源；无法访问时报告缺口，不擅自替代。
- 区分当前实现、已确认需求、已确认决策和未决方案。具体冲突按 [规划规则](references/planning-rules.md) 的“证据与冲突”处理。
- 只有缺失信息会改变文档含义、范围或正确性时才提问；继续处理不受影响的部分。需要探索项目想法时，指出具体缺口并按“职责边界”交还上游，不自行扩展成需求访谈。

**完成条件：**知道本轮读者任务、处理范围、主要证据及尚未确认的部分。

### 2. 按读者任务规划文档变更

涉及新文档、结构调整或持续维护范围判断时，读取 [Documentation Planning Rules v0.5](references/planning-rules.md) 的相关部分。局部修订先定位受影响信息的权威维护位置，不启动全库文档盘点。

对受影响的信息给出紧凑的规划记录：

| 信息 / 读者任务 | 来源与状态 | 权威位置（文件或章节） | 动作与理由 | 验证方式 |
| --- | --- | --- | --- | --- |

仅列本轮涉及的条目；简单修订用一句话代替表格。已有权威信息可以只链接，不要求搬入仓库。规划记录只为本轮成稿和验证服务，默认放在回复中；不另建规划、盘点或审查报告文件，除非用户或项目流程需要持久保存。

- **仅规划：**交付动作、必要时的目标目录、理由及未决项，到此结束。
- **仅审查：**先报告影响读者的具体问题、位置、证据和最小修复建议；不要直接改写。
- **已授权编写或维护：**默认直接完成当前有依据的文档工作，不为常规局部修改重复请求批准。涉及外部发布或实质改变需求、决策时，遵循相应授权与评审流程。

编写和维护支持两种工作方式，不要求每次先选择模式：

- **直接完成（默认）：**整体理解当前任务后，规划、编写并验证相应文档，交付结果和剩余缺口。
- **共同打磨：**用户要求“陪我梳理”“逐篇讨论”“先讨论再写”，或明确希望参与内容判断时，围绕当前文档或部分内容给出有依据的草稿和需要判断的问题，根据反馈修订，再按约定推进。先讨论时在回复中呈现草稿，不提前落盘；授权共同编辑后可修改约定范围，不擅自扩展到其他文档。

两种方式适用于新旧项目，遵守同一质量标准，可按用户要求切换。局部信息缺口只需澄清相关问题，不自动切换为整套访谈；共同打磨也不扩展为需求探索。

**完成条件：**已经知道要支持哪个读者任务、信息放在哪里以及如何验证。每个新增文件都有独立存在的理由；若现有结构已能让读者找到、理解和使用信息，可以不改结构。

### 3. 写出可读、可用的正文

成稿前先用一句话说明：“这位读者来这里是为了什么，读完后应能理解、决定或完成什么？”正文中的每一节都应直接支持这个结果。

- 先确认合适的入口。正式项目缺少项目级入口时通常使用 README；已有有效文档站、模块入口或用户指定范围时，只在导航确实受影响时更新 README。整理上游已确认结论时，可按规划规则选择项目简报，不强制同时创建 README。
- 先给出读者最需要的结论、状态或动作，再按依赖顺序补充背景。标题应说明主题或任务；每段承担一个主要作用，段首让读者知道接下来会得到什么。
- 把证据转成解释，不把代码、测试、提交记录或访谈原文堆给读者。描述行为时写清适用版本或范围、输入、可观察结果和限制；描述决定时区分结论、理由、取舍和后果；无法确认的内容保持为未知或提案。
- 写明容易被作者默认的关系：谁执行什么、前提如何影响动作、动作产生什么结果、一个组件为何依赖另一个。首次使用必要术语时用当前语境解释；只有具体示例能消除歧义或帮助完成任务时才加入示例。
- 操作说明给出一条可执行路径：先决条件、按顺序的动作、可识别的成功结果，以及当前任务需要的常见失败处理。会修改数据或环境的命令说明影响和可用恢复方式；没有证据时不编造故障处理。
- 使用与读者相符的具体名词和动词，删除不承载信息的开场、重复结论和装饰性表达。优先熟悉、自然的说法，但不为简短牺牲准确术语、必要条件、例外、理由或示例。交付可复制的 Markdown 草稿时，若正文包含代码围栏，应使用更长的外层围栏或不加外层围栏，并检查渲染后结构仍完整。
- 文档语言优先遵循用户明确要求，否则沿用目标文档或项目现有语言；没有可沿用语言时使用用户当前交流语言。保留代码标识符、命令和协议名称，不因对话语言而翻译它们。
- 参考资料优先以代码注释、Schema 或 CLI 帮助为生成源；修改生成源，不手写第二份完整参考。摘要、示例和链接可以为当前读者保留，但完整契约、需求或参数表只在权威位置维护。读者不应为了理解一句话连续跳转多份文档。
- 图表只在关系、顺序或比较比文字更清楚时使用；架构图应解释系统关系，不能只列目录名。不给每个文件强套章节、元数据或模板。
- 历史设计保留当时的状态和范围；当前行为放在持续维护的说明中。示例使用占位符，不写入凭据、用户隐私或机器专属路径。只修改本轮范围内的文档及必要链接，不顺带修复实现。

完成初稿后，从读者入口顺读一次：能否快速找到目标信息，是否需要猜测关键条件，能否辨认下一步和成功结果。根据发现补足解释或删去干扰内容，而不是按篇幅增删。

### 4. 按变化维护受影响内容

持续维护是一种按变化触发的任务，不是后台监控或定期治理：

- 用户明确要求维护文档时触发；当前已授权任务改变了读者可观察的行为、接口、命令、配置、路径、版本支持、限制、决策状态或导航时，也应更新其直接影响的文档。实现内部重构、文件日期变化或“顺便整理”本身不触发。
- 从“变化的事实或决定”向外检查：先找权威维护位置，再检查依赖它的入口摘要、操作示例和链接。只检查这条影响链；除非变化横跨项目或用户要求全面维护，不启动全库审计。
- 权威内容仍然准确、可发现且足以支持读者任务时，可以不改。需要修改时，同时清理本次变化造成的旧说法；不要借机重排无关文档或建立负责人矩阵、同步清单和进度报告。
- 多轮维护从现有文档和新增证据继续，不重新生成整套文件。无法访问外部权威来源时说明哪些内容未核对，只暂停依赖它的更新，不承诺自动追踪未来变化。

**完成条件：**受影响的权威内容、必要摘要、示例和导航彼此一致；未受影响的文档保持原状。详细影响判断见规划规则的“维护触发与影响范围”。

### 5. 验证与交付

按本轮读者任务和变更风险验证，不为文档数量或测试数量扩展工作：

1. **事实：**核对命令、路径、参数、接口、版本和状态。关键结论能追溯到代码位置、适用版本或已确认记录；不会从测试通过推断全部行为正确。
2. **使用：**能安全执行时，在隔离环境验证受影响的快速开始或示例，观察实际结果。无法执行时明确写“仅静态核对”及原因；未验证的步骤不能声称可用。
3. **读者任务：**从实际入口完成一次查找、理解或操作，检查读者是否必须猜测关键条件。改写前列出必须保留的信息，改写后逐项确认事实、限制、例外、理由和安全条件的去向。
4. **写作质量：**按下表检查本轮涉及的文档，并检查标题层级、列表、表格、代码围栏和链接文本在目标渲染器中保持完整。简洁是去掉无助于任务或妨碍理解的表达；有助于理解的背景、示例、图解和摘要应保留，缺失时按证据补充。
5. **维护影响：**若任务由变化触发，核对权威位置以及受影响的摘要、示例和导航；不把一次局部变更声称为全库同步完成。
6. **结构与范围：**检查失效入口、相对链接和渲染，运行项目要求的文档检查；审阅完整 diff，确认没有改写已确认需求、捏造决定、误删历史、覆盖用户修改或扩展到无关文档。没有既有检查时，不为本次写作引入新工具链。

| 文档 | 可读性 | 准确性 | 简洁性 | 完整性（限当前任务） |
| --- | --- | --- | --- | --- |
| README | 首次读者能找到用途、状态、起步和深入入口 | 能力、支持范围和示例有证据，不把计划写成可用功能 | 合并重复介绍，移走有独立职责的细节，保留入口上下文 | 保住适用对象、必要前提、最小用法、关键限制及已有帮助/许可入口；缺失信息不编造 |
| 技术文档（含需求、规格、架构、设计、ADR） | 术语一致，行为、关系或决定的叙述可追踪 | 区分现状、需求、决定与提案，标明必要的范围和来源 | 避免机械复述代码或重复维护完整契约；保留理解所需的解释、示例、理由与链接 | 按职责保住验收条件、接口与异常、系统边界或决策后果，不要求每份覆盖全部类型 |
| 操作指南 | 前提在先，步骤可执行，结果可识别 | 命令、参数、路径及版本适用性经过核对，注明未执行部分 | 保留执行所需的动作与背景，完整参考用链接承接 | 保住必要权限/环境、输入、预期结果、常见失败处理；有破坏性操作时说明影响及可用恢复方式，无法恢复须明确 |

交付说明包含：解决了哪些读者问题、改了什么及原因、文档入口、实际完成的检查、未覆盖的行为和待解决冲突。评价改进时说明查找、理解或使用上的具体变化；没有读者测试时，不声称阅读速度或理解效果已得到实测证明。没有问题也不宣称穷尽正确。

**完成条件：**直接完成时，本轮能够完成的读者任务有充分信息支持，文档可发现，事实状态明确；共同打磨时，交付本轮约定的草稿或修订，并说明待反馈部分，不把阶段草稿当作已完成的整套文档。未验证项和阻塞项可见，只阻塞依赖它的内容。
