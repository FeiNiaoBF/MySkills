# project-docs

依据代码、已有文档、已确认需求和讨论记录，为新项目逐步建立文档，为已有项目持续整理和维护文档。目标是让 Agent 基于可靠事实，写出读者愿意读、能理解、实际有用、以后能维护的文档。结构只服务于读者任务；不把目录完整、文件数量、负责人字段或例行盘点当作文档质量。

本文与参考中的“必须”是执行约束；“建议”“默认”可按项目事实调整并说明理由。

## 职责边界

- **负责**：规划、编写、改写和维护项目文档，并识别为完成这些工作的具体修复项。
- **只读判断**：主要产物是判断某对象是否适合某用途，而非继续写或维护时，只给判断，不启动文档工作流。
- **UI 视觉与组件规范**：视觉语言、设计令牌、组件用法、变体、状态和设计系统规则属于独立 UI 设计文档任务；项目需求、外部行为规格、内部技术设计、系统架构和 ADR 仍属本 Skill，文件名 `DESIGN.md` 不能单独决定任务类型。
- **未决目标与决定**：目标、需求或决定尚未形成时，指出会改变文档含义的具体缺口并交还用户；只整理已有依据，不代替探索、访谈或决策。
- **实施排序**：实现顺序、依赖和最小可交付切片属于实施规划；只有其中确需正式项目文档时，本 Skill 才负责写作。文档不是实施工作的固定前置阶段。

按用户期望的主要产物选择任务方式。隐式触发且边界不清但不改变现有文档内容时，直接完成有依据的部分，不先组织额外流程；主动调用按下一节确认。

## 主动调用时的入口确认

用户点名本 Skill（如“用 project-docs …”）或要求按本流程处理时，先只读扫描，不修改任何文件；扫描与选项确认完成前不进入写作。

1. **扫描项目。** 查看顶层目录、文档入口和现有分工：`README`、`CONTRIBUTING`、`docs/`、需求、规格、ADR、指南等；确认权威维护位置、各自面向谁、版本库近期变化。排除依赖、构建产物、缓存和版本库内部文件；只读到能判断文档结构和影响范围，不逐篇通读；外部 Wiki、需求系统等不可访问时记为缺口。先检查工作区改动，保留用户未提交内容。此步只建立结构和影响地图，不替代执行流程第 1 步的证据核对。
2. **一次列全三个选项。** 不逐项追问，也不只给推荐项；每个选项写明会动哪些文件或目录、影响多大、是否需要再次确认。请求已限定单篇或单段时，选项 A 的范围就是该文件或段落，不扩到全库。
   - **A. 保持现有结构**：不改目录、文件名和职责，只在现有结构内完成本轮请求；列出预计修改的文件、读者可见变化和明确不动的部分。
   - **B. 按项目上下文重排**：依据项目证据提出目录与职责调整（合并、拆分、迁移、新建或归档），列出每个受影响文件及范围。选 B 只允许提方案；改动任何文档内容前会再问是否允许修改、希望怎样让文档更清晰，未确认前不落盘。
   - **C. 由你决定**：不预设方案，由用户指定改哪些部分、改成什么样；列出候选文件和可改范围供选，不替用户选，选定前不改文件。
3. **说明边界与等待选择。** 给出已确认事实、未确认部分、扫描未覆盖来源，以及各选项对读者、链接和现有职责的影响。用户选定前不执行，不合并执行三个选项，不默认（也不以“更安全”为由）选 A。选定后按授权范围推进；仍缺具体文件或目标时，只补问完成该选项所需的最小信息。用户明确要求跳过选择时，按给定范围执行，不自行扩大。

完成条件：扫描结果、三个选项及各自会动的文件或目录、影响范围已一次给出；未修改任何文件；等待用户选择。

## 执行流程

### 1. 确定范围并读取证据

主动调用时先完成上一节；隐式触发时先检查工作区改动，保留用户内容。

- 识别本轮是规划、编写、审查还是维护，以及涉及的项目、功能和版本。结合材料确定主要读者、知识背景和阅读任务，不默认读者懂开发者黑话；沿用已有目标，不重复访谈。
- 读适用的项目约定、文档入口和本次材料，再沿信息缺口检查代码入口、接口、配置、测试或需求记录。未限定单篇时先从整体关系判断要补充、更新或调整什么；局部修改只查相关内容。新项目没有代码或文档时，从已确认资料起步，不预建完整目录。
- 新建或大改时，先从讨论、issue、提交和评审记录提取约束、被否方案、干系人、时间压力和既往事故；仍不足时请用户一次性补齐，不逐问访谈。
- 每次调用都依据当前材料完成有价值且有证据支持的工作；新代码、新需求或新决定出现后，核对并更新受影响文档。渐进完善不限定每次只写一篇，也不要求首次完成整套文档。
- 仓库外的 Wiki、需求系统或文档站也可能是权威来源；不可访问时报告缺口，不擅自替代。
- 区分当前实现、已确认需求、已确认决定和未决方案；具体冲突按 [规划规则](references/planning-rules.md) 的“证据与冲突”处理。
- 只有缺失信息会改变文档含义、范围或正确性时才提问，其余部分继续做。需要探索项目想法时，指出具体缺口并按“职责边界”交还上游，不自行扩展成需求访谈。

完成条件：知道本轮读者任务、处理范围、主要证据及尚未确认的部分。

### 2. 按读者任务规划文档变更

涉及新文档、结构调整或持续维护范围判断时，读 [规划规则](references/planning-rules.md) 的相关部分；局部修订先定位受影响信息的权威位置，不启动全库盘点。

对受影响的信息给出紧凑的规划记录（仅列本轮条目；简单修订用一句话代替表格；已有权威信息可只链接，不搬入仓库；默认放回复中，除用户或项目流程要求持久保存外，不另建规划、盘点或审查报告文件）：

| 信息 / 读者任务 | 来源与状态 | 权威位置（文件或章节） | 动作与理由 | 验证方式 |
| --- | --- | --- | --- | --- |

- **仅规划**：交付动作、必要时的目标目录、理由和未决项后结束。
- **仅审查**：报告影响读者的具体问题、位置、证据和最小修复建议，不直接改写。
- **已授权编写或维护**：默认直接完成当前有依据的工作，不为常规局部修改重复请求批准；涉及外部发布或实质改变需求、决策时，遵循相应授权与评审流程。

编写和维护支持两种方式，不要求每次先选：**直接完成（默认）** 是整体理解后规划、编写、验证并交付结果与剩余缺口；**共同打磨** 在用户要求“陪我梳理”“逐篇讨论”“先讨论再写”或希望参与内容判断时启用，围绕当前文档给出有依据的草稿和待判断问题，按反馈修订后推进。先讨论时草稿放回复中，不提前落盘；授权共同编辑后只改约定范围，不扩展到其他文档。两种方式适用于新旧项目，遵守同一质量标准，可随时切换；局部缺口只澄清相关问题，不升级为整套访谈，共同打磨也不扩展为需求探索。

完成条件：知道要支持哪个读者任务、信息放在哪里、如何验证。每个新增文件都有独立存在的理由；现有结构已能让读者找到、理解和使用信息时，可以不改结构。

### 3. 写出可读、可用的正文

成稿前先用一句话说明：“这位读者来这里是为了什么，读完后应能理解、决定或完成什么？”每一节都直接服务这个结果。

- README 工作按 [README 规则](references/readme-rules.md) 执行。
- 写或改写正文前读 [写作规则](references/writing-rules.md) 并按其执行：短常用词、主动语态、一词一义、删冗余、条件先于动作。英文文档执行 Orwell 六原则和 ASD-STE100 的句长/结构约束；中文文档应用等价原则，不机械套用英文词表、句长或冠词规则。
- 把证据转成解释，不把代码、测试、提交记录或访谈原文堆给读者。写行为时写清适用版本或范围、输入、可观察结果和限制；写决定时写清结论、理由、取舍、后果、非目标、接受代价和复访条件。备选方案只在材料中真实出现过时记录，不补造；无法确认的内容保持为未知或提案。
- 写明容易被默认跳过关系：谁执行什么、前提如何影响动作、动作产生什么结果、组件为何依赖另一个。只有具体示例能消歧或帮助完成任务时才加，使用占位符，不写凭据、隐私或机器专属路径。
- 语言优先用户要求，其次目标文档或项目语言，再次当前交流语言；不翻译代码标识符、命令、协议名和 API 名。
- 交付可复制的 Markdown 草稿时，正文含代码围栏则用更长的外层围栏或不用外层围栏，并检查渲染后结构完整。
- 参考资料优先以代码注释、Schema 或 CLI 帮助为生成源，改生成源，不手写第二份完整参考；摘要、示例和链接可为当前读者保留，但完整契约、需求或参数表只在权威位置维护，读者不应为理解一句话连跳多份文档。
- 图表只在关系、顺序或比较比文字更清楚时使用；架构图解释系统关系，不能只列目录名。不给每个文件强套章节、元数据或模板。
- 历史设计保留当时的状态和范围，当前行为放在持续维护的说明中。
- 只改本轮范围内的文档及必要链接，不顺带修复实现。

完成初稿后从读者入口顺读一次：能否快速找到目标信息、是否需要猜测关键条件、能否辨认下一步和成功结果。按内容补足或删减，不按篇幅增删。

### 4. 按变化维护受影响内容

持续维护由变化触发，不是后台监控或定期治理：

- 用户明确要求维护文档时触发；当前已授权任务改变了读者可观察的行为、接口、命令、配置、路径、版本支持、限制、决策状态或导航时，也更新其直接影响的文档。实现内部重构、文件日期变化或“顺便整理”本身不触发。
- 行为变化与文档更新尽量同属一个变更集；项目已有 PR 模板、CI 文档检查或贡献清单时按它挂接，没有则不新建流程。改名或退役术语时，用全库检索辅助清理入口、示例和导航；检索只作线索，不替代语义判断。
- 从“变化的事实或决定”向外检查：先找权威位置，再查依赖它的入口摘要、操作示例和链接。只查这条影响链；除非变化横跨项目或用户要求全面维护，不启动全库审计。
- 权威内容仍准确、可发现且足以支持读者任务时，可以不改；需要修改时同时清理本次变化造成的旧说法，不借机重排无关文档或建立负责人矩阵、同步清单和进度报告。
- 多轮维护从现有文档和新增证据继续，不重新生成整套文件。外部权威来源不可达时说明哪些内容未核对，只暂停依赖它的更新，不承诺自动追踪未来变化。

完成条件：受影响的权威内容、必要摘要、示例和导航彼此一致；未受影响的文档保持原状。详细判断见规划规则的“维护触发与影响范围”。

### 5. 验证与交付

按本轮读者任务和变更风险验证，不为文档或测试数量扩展工作：

1. **事实**：核对命令、路径、参数、接口、版本和状态；关键结论能追溯到代码位置、适用版本或已确认记录；不从测试通过推断全部行为正确。
2. **使用**：能安全执行时在隔离环境验证受影响的快速开始或示例，观察实际结果；无法执行时写明“仅静态核对”及原因，未验证的步骤不声称可用。
3. **读者任务**：从实际入口完成一次查找、理解或操作，检查读者是否必须猜测关键条件。改写前列出必须保留的信息，改写后逐项确认事实、限制、例外、理由和安全条件的去向。
4. **写作质量**：按下表检查本轮涉及的文档，并按 [写作规则](references/writing-rules.md) 检查用词、句长、语态、术语一致性和语言适配；同时检查标题层级、列表、表格、代码围栏和链接文本在目标渲染器中保持完整。简洁是去掉无助于任务或妨碍理解的表达；有助于理解的背景、示例、图解和摘要应保留，缺失时按证据补充。
5. **维护影响**：任务由变化触发时，核对权威位置及受影响的摘要、示例和导航；不把一次局部变更声称为全库同步完成。
6. **结构与范围**：检查失效入口、相对链接和渲染，运行项目要求的文档检查；审阅完整 diff，确认没有改写已确认需求、捏造决定、误删历史、覆盖用户修改或扩展到无关文档。没有既有检查时，不为本次写作引入新工具链。

| 文档 | 可读性 | 准确性 | 简洁性 | 完整性（限当前任务） |
| --- | --- | --- | --- | --- |
| README | 读者能快速判断用途与适用性，找到起步路径和深入入口；使用者与维护者内容各在合适位置 | 能力、支持范围和示例有证据，不把计划写成可用功能 | 合并重复介绍，移走有独立职责的细节，保留读者判断所需的上下文 | 保住适用对象、必要前提、最小用法、关键限制及已有帮助/许可入口；缺失信息不编造 |
| 技术文档（需求、规格、技术设计、架构、ADR） | 术语一致，行为、关系或决定的叙述可追踪 | 区分现状、需求、决定与提案，标明必要范围和来源 | 避免机械复述代码或重复维护完整契约；保留理解所需的解释、示例、理由与链接 | 按职责保住验收条件、接口与异常、系统边界或决策后果，不要求每份覆盖全部类型 |
| 操作指南 | 前提在先，步骤可执行，结果可识别 | 命令、参数、路径及版本适用性经过核对，注明未执行部分 | 保留执行所需的动作与背景，完整参考用链接承接 | 保住必要权限/环境、输入、预期结果、常见失败处理；有破坏性操作时说明影响及可用恢复方式，无法恢复须明确 |

交付说明包含：解决了哪些读者问题、改了什么及原因、文档入口、实际完成的检查、未覆盖的行为和待解决冲突。评价改进时说明查找、理解或使用上的具体变化；没有读者测试时，不声称阅读速度或理解效果已实测提升。

完成条件：直接完成时，本轮能完成的读者任务有充分信息支持，文档可发现，事实状态明确；共同打磨时，交付约定草稿或修订并说明待反馈部分，不把阶段草稿当作已完成的整套文档。未验证项和阻塞项可见，只阻塞依赖它的内容。
