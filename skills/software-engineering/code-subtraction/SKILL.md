# code-subtraction — 代码与项目「做减法」

帮助工程师识别并移除有证据表明不必要的复杂度。目标是让系统更容易理解、验证和修改，不是单纯减少代码行数。

详细场景、判断依据和可选报告格式见 [references/subtraction-playbook.md](references/subtraction-playbook.md)。

## 核心原则

- **先确认价值与边界**：候选代码没有明显调用，不等于没有外部、动态或运维用途。
- **按上下文判断抽象**：重复是调查信号；只有合并后能减少知识重复，且不会显著增加耦合、跳转成本或性能负担时，才抽象。
- **保留简单、局部、可验证的实现**：复杂度是否多余，取决于需求、调用方、变化方式和维护成本，不由行数或固定次数决定。

## 工作流程

### 1. 明确目标和范围

区分用户需要的是减法分析建议，还是已经授权实施删除。确认目标、受影响的功能/调用方，以及不应改变的行为、兼容性或性能要求。若只是概念性提问，直接解释即可。

### 2. 收集候选项证据

查看候选项的引用关系、入口配置、动态调用、生成代码、插件约定、运行路径和维护历史。使用项目现有的静态分析、依赖工具、文档和验证手段。把观察到的事实与推断分开；仅凭搜索无引用或一次未执行，不足以证明可删。

### 3. 按影响和证据评估

综合判断影响面、可逆性、兼容性、性能要求和证据质量。风险级别可作为沟通摘要，但不是删除门槛：

- **低**：局部且易恢复，引用和用途清楚，现有静态检查足以支持判断。
- **中**：涉及内部边界、配置或多个调用方，需要更完整的调用链、构建或行为验证。
- **高**：公共 API、线上功能、数据/安全边界或性能关键路径；先确认依赖方、迁移与回滚方案，必要时分阶段弃用。

证据不足时说明不确定性、建议补充的证据或暂缓项。没有测试不自动代表不能删，也不代表可以盲删；依据风险寻找替代验证，必要时先补能覆盖关键行为的检查。

### 4. 提出建议或实施获授权的改动

每个候选项说明位置、为何可能多余、建议动作、影响和验证方法。只在当前任务授权包含实施时修改代码。尽量一次处理一个可独立理解的改动；不把无关重构混入删除。

### 5. 按影响验证并报告

遵循项目的验证约定，选择与影响相称的静态检查、构建、测试、接口兼容或性能对比。消融对照只用于风险较高、行为影响不明或现有证据不足的候选项：在隔离且可回滚的环境中一次移除一个候选项，复现相关基线并比较结果。结果无差异只支持当前验证范围内的结论，不证明所有配置、未来需求或未覆盖路径都不受影响。

分析任务可使用 playbook 中的可选「减法分析报告」格式；简短问题不需要套用完整报告。

## 谨慎处理的情况

公共 API、跨服务功能、数据迁移、错误处理、安全边界和性能关键代码，先分析兼容性及失败后果，再选择渐进式弃用或更强验证。线上或共享系统的变更应按项目流程准备影响说明、备份/回滚和观察方式；普通本地清理无需机械套用发布周期。
